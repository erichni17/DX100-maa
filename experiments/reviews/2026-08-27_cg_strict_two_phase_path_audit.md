# CG strict two-phase path audit (2026-08-27)

## Decision

Scott's `all B descriptors -> all A issues` schedule must gate **both real
16K indirect stages** of the selected full CG path:

1. the p-side virtual gather (including the fused p16 producer), and
2. the q-side page-fed 16K RMW.

It must not be described as a whole-CG strict reference when only the q16
page-fed stage is gated. `direct4_product_page_fed_q16` deliberately replaces
the p-side 16K gather with four ordinary physical 4K gathers, so it is a useful
q16-only control but cannot validate Scott's p16 schedule.

The meeting definition is in
`/data1/nier/dx100-research/docs/meetings/meeting_review_2026-08-24.md`:
each B value is fetched once; Row/Offset metadata, not raw B, survives; and
`A_FIRST_ISSUE >= ROW_OFFSET_LAST_INSERT`. The full-CG profile identifies the
old producer's index publication/re-read as redundant, rather than evidence
against this retained-16K reference
(`experiments/analysis/cg_full_overhead_profile_2026-08-25.md`).

## Exact ownership map

| CG stage | B / index owner | A / scattered line owner | P / value owner | Q / update owner | Row/Offset owner |
| --- | --- | --- | --- | --- | --- |
| Plain virtual p gather | `colidx[k_base + logical]` in `cg.cpp` | `p` (or `z` in residual SpMV) | virtual coherent gather backing | later page-local `P=A*a` | `IndirectAccessUnit::fillRowTable`; `RT[my_RT_config]` holds A line/row, `offset_table` holds logical ordinal/word alias |
| Fused p16 producer | the `indices` argument to `cg_fused_p16_product` | its `source` (`p` or `z`) | `cg_soa_products[tid]`; coefficient is `a[k_base + logical]` | later q16 RMW | the same p-side `RT`/`offset_table`; the fused response state only supplies coefficient/product work |
| Page-fed q16 RMW | physical q-index tile `t0`, generated by `maa_range_loop` and admitted in page order | `curr_q` or `curr_r` destination line | `cg_soa_products[tid]`, read by retained source ordinal | `ADD` to the destination A line, then exact coherent write response | q-side `insertPageFedSoaJitIndex` inserts `ordinal,wid` into `RT`/`offset_table`; `serviceSoaJitBuild` claims a destination line |
| Direct4 producer + q16 | four physical `colidx` pages | `p`/`z` gathered by ordinary `maa_indirect_load` | physical `t7` product page response-published to `cg_soa_products` | same q16 RMW | no retained 16K p Row/Offset state; q is page-fed as above |

`P` is a product **value**. It is not a RowTable entry and does not replace
the B-derived descriptor. `OffsetTable` ownership is per indirect operation:
it carries a logical ordinal and word-within-line link for the operation's
selected A line; it is neither the P backing nor a cross-stage 16K descriptor
array. Thus p and q need separate strict timelines even when they are in one
CG SpMV window.

## Real paths, not labels

The guest selector is `CgRmwTreatment` in `benchmarks/NAS/cg/cg.cpp`.

- **Plain page-fed p16/q16:** `maa_indirect_load_virtual_index<float>` issues
  the 16K p gather. After its backing is complete,
  `cg_page_fed_product_open`, `cg_page_fed_admit_product_page`, and
  `cg_page_fed_product_close` form one q-side SoA/JIT RMW. This is the path
  named `page_fed_product_soa_jit` by
  `experiments/scripts/run_cg_page_fed_p16_q16_value_cache_full.py`.
- **Fused p16/q16:** `cg_fused_p16_product` invokes
  `maa_indirect_load_virtual_index_product_fp32`, which gathers p/z, fetches
  `a`, and writes only final products to `cg_soa_products`. It then opens q
  with `cg_page_fed_q16_open`; each `cg_page_fed_admit_q_index_page` supplies
  its q index page; `cg_page_fed_q16_close` starts q execution. The simulator
  implementation is `IndirectAccessUnit::beginFusedP16ResponseHead`,
  `drainVirtualResponses`, and `checkFusedP16Terminal` for p, and
  `admitPageFedSoaJitIndexPage`/`serviceSoaJitBuild` for q.
- **Direct4/q16:** `cg_direct4_publish_product_page` performs four physical
  `maa_indirect_load` plus ALU product operations and publishes P. Only after
  those publisher completions does `cg_page_fed_q16_open` regenerate the four
  q index pages. The full runner correctly declares
  `p16_reorder_preserved=0` and `q16_reorder_preserved=1` in
  `run_cg_direct4_product_page_fed_q16_full.py`.

The architectural q path is unambiguous: `PageFedSoaJitState::close` and
`beginExecution` protect closure; `IndirectAccessUnit::insertPageFedSoaJitIndex`
translates each index and inserts it into `RT`; then
`IndirectAccessUnit::serviceSoaJitBuild` uses `claim_entry_send` and
`createReadPacket` to issue the destination/A read. Values are acquired by
`issueSoaJitValueRead` and applied by `applySoaJitValue`; `issueSoaJitWrite`
and `completeSoaJitWrite` close the coherent update.

## Required strict integration contract

Enable strict mode only for a 16K logical / 4K physical operation with all of
the following, fail closed on every violation.

1. **p timeline:** exactly 16,384 B words are fetched once and admitted into
   the p Row/Offset structures; no drain, replay, direct4 substitution, or
   A issue precedes p admission closure. Record B begin/end, first/last
   insert, first/last A issue/response, backing issue/ack, and page ready.
   Apply this to both `maa_indirect_load_virtual_index` and
   `maa_indirect_load_virtual_index_product_fp32`.
2. **q timeline:** exactly four 4,096-word q pages are admitted in logical
   order, `PageFedSoaJitState::close` succeeds, and the actual packet edge
   (`createReadPacket`), not only a state transition, checks
   `A_FIRST_ISSUE >= ROW_OFFSET_LAST_INSERT`. It must also report product
   publication response closure, P value-read/delivery closure, q backing
   write/ack closure, and consumer begin/end.
3. **whole-window link:** a strict p16/q16 claim requires the p terminal
   generation, all four P page responses, the q generation, and CG's full
   numerical/response-ledger terminal to be linked in one record. A q-only
   run must be labelled `q16_only`; direct4 must be labelled
   `p16_bypassed_direct4`.
4. **full workload gate:** compile `benchmarks/NAS/cg/cg.cpp` with the same
   full-CG geometry and treatment selector as the selected runner, require
   all expected full windows and both SpMV routes, exact fingerprint/numerical
   checks, no fallback/epoch drain, exact publisher responses, and the strict
   event order for every p and q operation. A static source test may protect
   symbols, but cannot satisfy this gate.

## Active strict worker review (read-only)

Worktree `codex/session-strict-two-phase-cg-reference-20260827-20260827-182028-096a7ac2`
has uncommitted simulator work. It is headed in the right direction for two
separate local guards:

- `IndirectAccessUnit::strictTwoPhaseOperation`,
  `MAA::beginStrictTwoPhaseReference`, and `StrictTwoPhaseReference` reject
  p-side capacity drains and check the plain/fused virtual direct-index
  timeline.
- `IndirectAccessUnit::strictPageFedTwoPhaseOperation` records page-fed
  admission and calls `PageFedSoaJitState::authorizeAIssue` at
  `createReadPacket`, so it guards the actual q A issue.

It is not yet an integration-ready whole-CG reference. The q-only
`strict_page_fed_*` fields have no terminal event/ledger equivalent to
`MAA::completeStrictTwoPhaseConsumer`; `strict_page_fed_consumer_end_tick` is
only reset in the shown diff. Consequently its current q guard can panic on
an early A issue but cannot prove, emit, or join all required q timing,
backing/page, and consumer closure to p. No guest selector or runner diff is
present, so the new option cannot yet prove that a full `cg.cpp` fused or
page-fed path actually exercised both legs. This should remain a diagnostic,
default-off mode until the contract above is added.

## False-positive modes to reject

- `benchmarks/API/test_cg_product_handoff.cpp` is a valuable bitwise
  publication microprobe, but `runOneUsefulLogicalSoaJitAdd` has one useful
  descriptor and synthetic destinations. It does not execute full CG, its
  p virtual gather, both SpMV routes, or a complete p-to-q window.
- `run_cg_fused_p16_product_q16.py` explicitly accepts only `CG_NA=256` (10
  windows) or confirmed `CG_NA=1024` (65 windows) and says native/full are
  forbidden. A pass is a bounded successor screen, not a full-CG strict
  result.
- `direct4_product_page_fed_q16` can pass its full-CG q16 checks while
  bypassing the p16 reorder engine by design. It must never be promoted as
  proof of a strict all-descriptors-before-A p16 schedule.
- A plain virtual-gather-only strict pass omits q's page-fed RMW; conversely,
  page-fed-only strict accounting omits p when direct4 is selected. Neither
  establishes the selected p16/q16 integration.

No simulator source was modified and no gem5 execution was performed for this
review.
